
## New lifestyle features

- **Forgot password:** the sign-in screen links to a one-time password-reset link. Tokens are stored as SHA-256 hashes, expire after 30 minutes, and are invalidated after use. Email delivery requires SMTP configuration below. If SMTP is not configured, the app intentionally does not show or log reset tokens.
- **Health & nutrition:** each signed-in account can log water and food portions. The dashboard calculates logged water, calories, protein, carbohydrates and fats for the current local day. Users can edit their daily target values; the initial values (2,500 ml water, 2,000 kcal, 50 g protein, 275 g carbohydrates and 78 g fat) are generic starting examples, not personalized medical recommendations. Entries and targets are scoped by account. The new wellness and fashion records are included in the authenticated cloud-to-PC snapshot.
- **Food library:** the current starter catalogue contains common foods from multiple regions with approximate per-100-gram values. These are estimates and are not a substitute for product labels or clinical nutrition advice; this is a starter catalogue, not literally every food in the world.
- **Fashion studio:** save private outfit ideas by occasion, style inspiration, upper/lower layers, footwear, accessories and notes. Outfits are tied to the signed-in account.

### Password-reset email settings on Render

Add these environment variables in the Render service settings. Use credentials from your email provider; do not put secrets in source code.

- `SMTP_HOST` — provider SMTP hostname
- `SMTP_PORT` — usually `587` for STARTTLS
- `SMTP_FROM` — verified sender address
- `SMTP_USER` — SMTP username, if required
- `SMTP_PASSWORD` — SMTP password or provider app password, if required

Password-reset email is deliberately disabled until at least `SMTP_HOST` and `SMTP_FROM` are configured. After changing environment variables, redeploy/restart the service. The existing `SECRET_KEY`, `DATABASE_URL`, `SYNC_TOKEN`, and `SYNC_USER_EMAIL` settings should remain configured as before.

# WILD_WITHIN_NEW — Cloud database + PC mirror

This update keeps the existing WILD WITHIN dashboard, activity timetable, free-time planner, Habit Lab, and history. It changes the hosted source of truth to PostgreSQL so the Render app keeps working while your PC is switched off. A Windows sync agent downloads an authenticated read-only snapshot to a persistent SQLite mirror on your PC.

## Important architecture notes

- **Cloud source of truth:** PostgreSQL, configured by `DATABASE_URL` on Render.
- **Local PC mirror:** `D:\WILD_WITHIN_DATA\wild_within_cloud_mirror.db` by default. This is a snapshot/mirror, not a second independently editable source of truth. Do not edit this file directly.
- **Automatic backup:** the sync script creates a daily `*_backup_YYYYMMDD.db` copy before replacing the mirror, and only replaces it after a full snapshot has been received and validated.
- **PC off:** Render continues to work. The PC mirror catches up the next time Windows runs the sync task and can reach the Render URL.
- **Media:** this version syncs the current app's database records. It does not yet implement video/photo uploads or media-object storage.
- **Accounts and data isolation:** users can sign up and sign in with individual email/password accounts. Passwords are stored as Werkzeug password hashes, never as plain text. Each account has private, per-user activity, log, experiment, and free-time records. The first account claims legacy unowned prototype records during signup so old data is preserved. Set a strong `SECRET_KEY` on Render. The snapshot endpoint is protected by `SYNC_TOKEN` and limited to the account in `SYNC_USER_EMAIL`.
- **Sync direction:** cloud → PC mirror. Do not edit the mirror and expect those edits to upload. The online app is the authoritative copy to avoid conflicting offline edits.

## Before deploying: preserve current data

1. **Do not delete or overwrite your current app folder or database.** Make a separate copy of your current project and `wild_within.db` first.
2. If the current SQLite database is on your PC, locate it. In the folder where you run the app, look for `wild_within.db`. Copy it to a safe location, for example `D:\WILD_WITHIN_DATA\pre_cloud_migration_wild_within.db`.
3. If the only database was on Render's temporary filesystem and has already been lost, a code update cannot recover those records. Export any records still visible before switching.
4. Deploy this project to a **new branch or a backup repository first**. Do not replace the live repository until you have verified the migration and deployment.

## Deploy on Render

1. Push this folder's contents to a GitHub branch/repository connected to Render.
2. In Render, create the PostgreSQL database and web service using `render.yaml` (Blueprint) or create them separately.
3. The web service must have `DATABASE_URL` set to the database's **internal connection string**. Do not put the database password in source code or commit it to GitHub.
4. Set `SECRET_KEY` to a long random secret and `SYNC_TOKEN` to a separate long random secret. Do not commit either to GitHub. Set `SYNC_USER_EMAIL` to the email address whose cloud records should be mirrored to this PC.
5. Deploy and check `https://YOUR-APP.onrender.com/health` returns `{"ok": true, ...}`. **Do not create your first account until the existing SQLite data has been imported**, if you have old local records to preserve. After import, open `/signup` to create your account and use a unique password of at least 12 characters.

### Import existing SQLite records into PostgreSQL

Do this **after** the PostgreSQL tables have been created and **before creating your first account**. The first account claims legacy rows that have no account owner, so signup before import would leave subsequently imported rows unassigned. Keep the original SQLite file untouched.

In PowerShell on your PC, from this project folder:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
$env:DATABASE_URL = "YOUR_POSTGRES_EXTERNAL_CONNECTION_STRING"
.\.venv\Scripts\python.exe tools\import_sqlite_to_cloud.py "D:\WILD_WITHIN_DATA\pre_cloud_migration_wild_within.db"
```

Use the **external** PostgreSQL connection string from Render only for this one-time migration from your PC. Treat it as a password. The importer is non-destructive: it inserts rows and skips conflicts; it does not delete or overwrite cloud rows. If you have multiple SQLite files, stop and identify the correct source before importing. Check activity/log counts after import. If you previously deployed a cloud schema with sample rows, review conflicts carefully before import.

## Configure automatic PC mirror sync

1. On your PC create `D:\WILD_WITHIN_DATA`.
2. In Windows Environment Variables, add:
   - `WILD_WITHIN_URL` = `https://YOUR-APP.onrender.com` (no trailing slash required)
   - `SYNC_TOKEN` = the exact same secret as the Render `SYNC_TOKEN`
   - Optional `WILD_WITHIN_LOCAL_MIRROR` = `D:\WILD_WITHIN_DATA\wild_within_cloud_mirror.db`
3. Close and reopen PowerShell/Command Prompt so it sees the new environment variables.
4. Run once manually from this project folder:

```powershell
.\.venv\Scripts\python.exe tools\sync_cloud_to_pc.py
```

5. Confirm `D:\WILD_WITHIN_DATA\wild_within_cloud_mirror.db` exists and the output says `SYNC OK`.
6. Open **Task Scheduler** → **Create Basic Task** → name it `WILD WITHIN Cloud Mirror Sync` → trigger **Daily**. In Advanced settings, repeat task every **5 minutes** for **1 day** (or choose your preferred interval). Action: **Start a program**. Program: the full path to this project's `.venv\Scripts\python.exe`. Arguments: the full path to `tools\sync_cloud_to_pc.py`. Start in: the project folder. Enable “Run whether user is logged on or not” if appropriate for your PC.
7. Test manually once after adding a new activity online. After the next scheduled run, check the sync log output/history and mirror file timestamp.

If your PC is off, no local sync can run while it is off; the cloud database continues storing data, and the PC mirror catches up on the next successful sync.

## Running locally

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe app.py
```

Without `DATABASE_URL`, the app uses SQLite in `wild_within.db` next to `app.py` (or the path in `WILD_WITHIN_DB`). With `DATABASE_URL`, it uses PostgreSQL. Do not point the production app at the mirror database.

## Limitations

- Current local mirror is cloud-to-PC only. It is not a two-way offline-edit synchronization engine.
- Browser reminders require the app/browser to be open; reliable background alarms require push notification infrastructure.
- This account-enabled prototype provides per-user row isolation, password hashing, session protections, CSRF checks on authenticated POST forms, and profile personalization. Before a larger public launch, add email verification, password reset, login rate limiting, security monitoring/audit logs, and proper media object storage.

## Live memories: photo posts and reels

The **Live memories** page adds a camera-first capture flow:

- Take a photo in the browser and publish it as a post, or record a short video reel (up to 90 seconds).
- Add/edit a title, caption, hashtags, and audience preference; retake by clearing the capture and recording again.
- Edit the text/audience later without altering the original media, or permanently delete a memory.
- Posts default to **Only me**. **Public** posts appear in the feed of other signed-in accounts. A follower graph is not implemented yet, so **Followers-only** posts remain private to their owner.
- Media is stored in the app database (PostgreSQL on Render when `DATABASE_URL` is configured), not on the browser or Render's temporary filesystem. Photos are limited to 8 MB and reels to 18 MB.
- The cloud-to-PC mirror includes post metadata and media. Since videos can be large, syncing media-heavy accounts can take longer and use more database/network storage; this is suitable for a small prototype, not a high-volume social network. For a larger launch, move media to object storage (such as S3-compatible storage) and use incremental media backups.
- Camera recording requires browser camera/microphone permission and HTTPS (the Render URL uses HTTPS). The browser must support `getUserMedia` and `MediaRecorder`; use a current Chrome or Safari browser.

**Note:** The audience setting is not a follower system, and this prototype does not yet provide video trimming, filters, cover-frame selection, comments, likes, follows, or direct messaging. Captions, tags, title, audience preference, and delete are editable now.


## PRESENT fashion discovery and music library

- **Bright PRESENT theme:** a luminous violet-and-gold interface with a light background, gradient discovery panels, and updated PRESENT navigation.
- **Fashion discovery:** links to current brand collections at Myntra, Zara India, and H&M India, plus live searches for celebrity-inspired outfit ideas. Retailer pages remain the source of truth for products, pricing, sizes, and stock; the app does not scrape or claim to synchronize retailer inventories.
- **My Style:** save starter outfit ideas with one click or create custom looks with occasion, style, garments, footwear, accessories, and notes. Saved looks are private to the signed-in account.
- **Music library:** create playlists by name and mood, save song titles, artist names, and HTTPS links from YouTube/YouTube Music, Spotify, and SoundCloud. Playlist data is stored in the app database and scoped to the signed-in account.
- **Playback:** YouTube links can be embedded when the URL contains a valid video ID. Other providers open their own player. Playback availability, embedding, catalogue access, and regional restrictions are controlled by each music provider.
- **Copyright and licensing:** PRESENT stores links and does not host, rip, or download songs. Full-catalogue streaming or offline listening would require a suitable licensed provider integration.
- **Deployment:** the music tables are created automatically at app startup. Keep the existing `DATABASE_URL` configured on Render for durable cloud persistence; without a configured persistent database, a local SQLite database may be lost if the host filesystem is ephemeral.
